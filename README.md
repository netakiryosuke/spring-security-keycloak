# ハッキング演習

## この教材について

架空のマッチングアプリ「よりあい」を題材にしたハッキング演習です。
ブラウザからの操作や通信の調査を通じて、情報漏えいとなりすましを体験し、原因となる実装と対策を学びます。

Java の基礎を学んだ人を想定しています。Spring Security や Keycloak の設定を一から実装する必要はありません。
まずは画面と通信を調べ、攻撃を体験した後でソースコードを読み、修正します。

**このアプリは、攻撃と対策を学ぶために意図的に脆弱性を含んでいます。**

**実際のサービスとして運用したり、インターネットに公開したりしないでください。** ローカルの演習環境でのみ使用してください。

**実際の個人情報や、他のサービスで使っているパスワードを登録しないでください。** 教材用の架空の情報だけを使用してください。

この教材では、次の二つの脆弱性を扱います。

- **認可漏れ**：操作する人の権限を確認せず、本来許可されていない情報まで返してしまう。
- **脆弱なパスワード**：他人が推測しやすいパスワードによって、なりすましを許してしまう。

## 準備と起動

### 必要なもの

- JDK 25
- Docker
- Chrome など、開発者ツール（DevTools）が利用できるブラウザ

この演習は `hacking-workshop` ブランチを使用します。

### 起動する

リポジトリのルートで実行します。

```bash
./backend/mvnw clean package
docker compose up -d --build
```

バックエンドの Docker イメージは、先に作成した JAR を取り込みます。初回起動時はイメージの取得や Keycloak の初期化に時間がかかります。

Keycloak が `healthy` になり、各サービスが起動したら [http://localhost:5173](http://localhost:5173) を開きます。

| 接続先 | 用途 |
|---|---|
| `http://localhost:5173` | よりあいの画面 |
| `http://localhost:8081` | バックエンド API |
| `http://localhost:8080` | ログインを担当する Keycloak |

### 最初に使うアカウント

「ログイン」から、次のテストユーザーでログインしてください。

| 項目 | 値 |
|---|---|
| ログインユーザー名 | `User` |
| メールアドレス（こちらでもログイン可能） | `user@example.com` |
| パスワード | `pass` |

「自分の情報を照会」を押し、自分のプロフィールと「自分だけのメモ」が表示されることを確認します。

## 認証と認可の基礎

似た言葉ですが、確認する内容が異なります。

| 用語 | 確認すること | 例 |
|---|---|---|
| 認証 | あなたは誰か | メールアドレスとパスワードでログインする |
| 認可 | あなたに何を許可するか | 会員情報を管理する操作は運営担当者だけに許可する |

**ログインできたからといって、すべての情報を見てよいわけではありません。**

### Keycloak とは

Keycloak（キークローク）は、ログインやユーザー管理などの機能を提供するオープンソースのソフトウェアです。
アプリごとにログイン機能を一から作る代わりに、認証を任せることができます。

「よりあい」でログインボタンを押すと、Keycloak が提供するログイン画面に移動します。
そこで入力したユーザー名やメールアドレス、パスワードを Keycloak が確認し、ログインに成功すると「よりあい」に戻ります。
情報の取得や操作を許可してよいかの判断は、この教材ではバックエンドが担当します。

### ログイン後の API 呼び出し

ログイン後、ブラウザは Keycloak からアクセストークンを受け取り、API を呼び出すときに次の HTTP ヘッダーを付けます。

```http
Authorization: Bearer <アクセストークン>
```

バックエンドはトークンを検証して、誰からのリクエストかを確認します。
そのうえで、対象の情報を返してよいか、操作を許可してよいかを判断する必要があります。
この演習では、トークンの内部構造や発行処理まで理解している必要はありません。

## 演習のお題とルール

### お題

**ユーザーネーム `osawa` の会員の「自分だけのメモ」を取得してください。**

最初に利用できるのは、前述のテストユーザーのアカウントだけです。
画面にない操作ができないか、通信から手がかりを探してみましょう。

取得できたら、そこに至る操作を説明できるようにしてください。

### ルール

- 操作対象は、自分のローカル環境で動かしたこの教材だけです。
- 攻撃を体験する段階では、管理者アカウントや Keycloak 管理コンソールは使用しません。
- 演習中に得た情報を使い、対象会員としてログインすることは認めます。
- 攻撃を体験する段階では、ソースコード、エクスポートファイル、DB から直接答えを探さないでください。コードを読むのは振り返りからです。
- 会員情報やパスワードを書き換えたり、データを削除したりする必要はありません。

## DevTools の使い方

まずは、画面が実行したリクエストと同じものを自分で送信してみます。
以下は Chrome での操作です。ブラウザの言語やバージョンによってメニュー名が異なる場合があります。

### 1. 画面の通信を観察する

1. よりあいにテストユーザーでログインします。
2. `F12` またはブラウザのメニューから DevTools を開き、**Network** タブを選びます。
3. 画面の「自分の情報を照会」を押します。
4. `http://localhost:8081/users/me` への `GET` リクエストを選びます。見つからない場合は **Fetch/XHR** で絞り込んでください。
5. **Headers** で送信先・メソッド・`Authorization` を、**Response** または **Preview** で返ってきた情報を確認します。

### 2. リクエストを編集して再送信する

次のいずれかの方法を選んでください。最初は URL を変えずに再送信し、画面操作と同じ情報が取得できることを確認します。

#### 方法 A：フェッチとして編集して再送信

1. Network の対象リクエストを右クリックし、**フェッチとして編集して再送信（Edit and resend as fetch）** を選びます。
2. Console に用意された `fetch(...)` のコードを確認します。この時点ではまだ送信されていません。
3. まずはそのまま実行します。変更して試す場合は、送信先の URL などを編集してから実行してください。
4. Network に新しく追加されたリクエストを開き、**Response** または **Preview** で結果を確認します。

コピーして貼り付ける操作を省けるので、このメニューがある環境ではこちらが手軽です。メニューがない場合は、方法 B または C を使ってください。

#### 方法 B：Copy as fetch

1. Network の対象リクエストを右クリックし、**Copy → Copy as fetch** を選びます。
2. **Console** タブに貼り付け、内容を確認して実行します。
3. Network に新しく追加されたリクエストを開き、**Response** または **Preview** で結果を確認します。

方法 A・B ともに、`console.log` を追加する必要はありません。Console 内で結果を見たい場合は、次の節の方法を使えます。

#### 方法 C：cURL

ターミナルで操作したい場合は、リクエストを cURL コマンドとしてコピーできます。

1. Network の対象リクエストを右クリックし、**Copy → Copy as cURL** を選びます。
2. ターミナルに貼り付け、送信先とヘッダーを確認して実行します。
3. レスポンス本文がターミナルに表示されます。HTTP ステータスとレスポンスヘッダーも確認したい場合は、`curl` に `-i` を追加してください。

以下はコマンドの形を示す例です。`<アクセストークン>` は自分の通信からコピーした値に置き換えてください。

```bash
curl -i "http://localhost:8081/users/me" -H "Authorization: Bearer <アクセストークン>"
```

コピー形式に **bash** と **cmd** の選択肢がある場合は、実行するシェルに合わせます。WSL・Git Bash・macOS・Linux のシェルでは bash 用、Windows のコマンドプロンプトでは cmd 用を使ってください。
PowerShell では上の 1 行の例を `curl.exe` に置き換えて実行できます。bash 用の複数行コマンドは、そのまま貼り付けないでください。

cURL の通信はブラウザの Network には表示されません。結果はターミナルで確認します。

### 3. Console 内で JSON を表示する場合

Console に用意した `fetch(...)` を `await (await fetch(...)).json()` で包むと、結果を Console で直接展開できます。
下は形を示す例です。`<アクセストークン>` は自分の通信からコピーした値に置き換えてください。

```javascript
await (await fetch("http://localhost:8081/users/me", {
  headers: {
    Authorization: "Bearer <アクセストークン>"
  }
})).json()
```

実際には、元のコードの URL やヘッダーを残し、先頭の `fetch(` を `await (await fetch(` に、末尾の `);` を `)).json()` に変更すれば同じ形になります。

最初は URL を変えず、同じリクエストを再送信してください。成功したら、送信先などを変えて挙動を調べてみましょう。

**ブラウザでログイン済みでも、直接書いた `fetch()` や cURL のリクエストにはトークンが自動では付きません。** どの方法でも、元のリクエストの `Authorization` を残すことが大切です。
アクセストークンは他人に渡さず、ログインし直した場合や期限が切れた場合は新しい通信からコピーしてください。

参考：[フェッチとして編集して再送信](https://chromium.googlesource.com/devtools/devtools-frontend/+/HEAD/front_end/panels/network/NetworkLogView.ts)、[Chrome DevTools の Network 操作](https://developer.chrome.com/docs/devtools/network/reference)、[Console での JavaScript 実行](https://developer.chrome.com/docs/devtools/console/reference)

## 何が起きたのか

<details>
<summary>演習後に開く：攻撃の流れと原因</summary>

1. テストユーザーでログインし、本人情報の取得リクエストを観察した。
2. 自分のトークンを使って `/users` を呼び出し、他の会員のメールアドレスと生年月日を取得した。（認可漏れ）
3. 対象会員の ID で `/users/{id}` を呼び出しても、管理者限定なので 403 になった。
4. 一覧から得た情報でパスワードを推測し、対象会員としてログインした。（脆弱なパスワード）
5. `/users/me` が返す対象会員の詳細から「自分だけのメモ」を取得した。

この教材には、二つの問題が組み合わさっています。

| 問題 | 結果 |
|---|---|
| 一覧取得 API に管理者かどうかの確認がない | 管理者でないユーザーにも他人の個人情報を返してしまう |
| パスワードが個人情報から推測できる | 漏れた情報を使って、別の会員としてログインできてしまう |

`/users/me` はリクエストで指定された ID ではなく、認証情報から本人の ID を取得します。
明示的な管理者チェックはありませんが、取得対象を本人に固定しています。
なりすまし後に他人の情報が見えるのは、対象会員の認証情報でログインしたためです。

画面でボタンを非表示にしても、API を直接呼び出すことはできます。
また、一つの API を保護していても、別の API から同じ情報や攻撃の手がかりが漏れる可能性があります。

### なぜ全件取得 API があるのか

実は、このアプリには運営担当者を想定した `Admin` ユーザーも用意されています。
`ADMIN` ロールを持っており、このユーザーでログインすると、画面に「全ユーザーを表示」ボタンが現れます。
全件取得 API の `/users` は、この会員管理機能で使うためのものです。

テストユーザーにはボタンを表示していませんが、バックエンドの `/users` には管理者かどうかの確認が抜けています。
一方、`/users/{id}` には管理者チェックがあります。この違いが、一覧は取得できるのに単一取得は 403 になる理由です。
管理者向けの機能では、画面の表示制御に加えて、API 側でも権限を確認する必要があります。

演習後は、次のアカウントで管理者向けの画面も確認できます。

| 項目 | 値 |
|---|---|
| ログインユーザー名 | `Admin` |
| メールアドレス（こちらでもログイン可能） | `admin@example.com` |
| パスワード | `pass` |

ログイン中の場合は一度ログアウトし、このアカウントでログインし直してください。
「全ユーザーを表示」を押すと、演習で直接呼び出した `/users` が画面から使われていることを確認できます。

</details>

## 実装を修正しよう

攻撃を体験したら、ソースコードを開きます。

<details>
<summary>修正課題と確認方法</summary>

次の順に処理を追い、一覧取得と単一取得の違いを探してください。

- [UserController.java](backend/src/main/java/com/netakiryosuke/spring_security_keycloak/presentation/UserController.java)：URL と処理の対応
- [UserApplicationService.java](backend/src/main/java/com/netakiryosuke/spring_security_keycloak/application/UserApplicationService.java)：会員情報を取得する処理
- [SecurityConfig.java](backend/src/main/java/com/netakiryosuke/spring_security_keycloak/config/SecurityConfig.java)：API 全体の認証設定

**修正課題：会員一覧の取得を管理者だけに許可してください。**

画面側の変更ではなく、API を直接呼び出しても拒否されるようにします。
本人情報の取得は、テストユーザーでも利用できる状態を保ってください。

修正したら、リポジトリのルートからビルドしてバックエンドを再作成します。

```bash
./backend/mvnw clean package
docker compose up -d --no-deps --build backend
```

テストユーザーに戻ってログインし、次を確認します。

| 操作 | 期待する結果 |
|---|---|
| 認証ヘッダーなしで一覧取得 | 401 |
| テストユーザーのトークンで一覧取得 | 403 |
| 画面から自分の情報を照会 | 200、自分の詳細情報 |
| テストユーザーのトークンで ID 指定の単一取得 | 403 |

修正前に成功した一覧取得を、同じテストユーザーの権限で再実行することが大切です。
その後、前述の `Admin` アカウントに切り替え、「全ユーザーを表示」で引き続き一覧を取得できることも確認してください。

</details>

<details>
<summary>修正例と振り返り</summary>

`UserApplicationService` の `list()` に、単一取得と同じ管理者チェックを追加します。

```java
@PreAuthorize("hasRole('ADMIN')")
public List<UserSummaryDto> list() {
    return userRepository.findAll().stream()
            .map(user -> new UserSummaryDto(
                    user.id(), user.username(), user.email(), user.birthDate()))
            .toList();
}
```

`@PreAuthorize` はメソッド実行前に条件を確認する仕組みです。
この例では、ログインしたユーザーに `ADMIN` ロールがある場合だけ処理を許可します。
必要な Spring Security の設定は教材側で用意済みです。

一覧 API を修正しても、既に知られてしまったパスワードが無効になるわけではありません。
認可漏れを直すことに加え、推測しやすいパスワードを変更する必要があります。
多要素認証なども対策になりますが、この演習では実装対象に含めません。

振り返ってみましょう。

- 画面にボタンがないことと、API で操作を拒否することは、どう違いましたか？
- 単一取得 API が 403 を返していても、なぜ目的の情報を取得できましたか？
- 一覧で返している個人情報は、本当にその利用者に必要でしょうか？
- 認可漏れを修正した後でも、対象会員としてログインできるのはなぜでしょうか？

</details>

## 困ったときは

| 症状 | 確認すること |
|---|---|
| API が 401 を返す | `Authorization` が付いているか確認。画面から本人情報を再取得して、新しいリクエストをコピーする |
| API が 403 を返す | 操作する権限がない場合の応答。何を取得しようとしたか、どのユーザーでログインしているかを確認する |
| Console に `Promise` や `Response` が表示される | Network の Response を開くか、`await (await fetch(...)).json()` の形で実行する |
| JSON の解析エラーになる | Network で実際の応答とステータスを確認。空の応答や HTML は JSON として解析できない |
| 画面に通信が記録されない | DevTools の Network を開いてからボタンを押す。記録が停止していないか確認する |
| 画面が開かない／`ERR_CONNECTION_RESET` | `docker compose ps` で起動状態を確認。`http://localhost:5173` を使用し、Chrome のシークレットウィンドウでも確認する |
| 画面が白いままになる | Console のエラーと Network の失敗した通信を確認。Keycloak の起動状態も確認する |
| Java の修正が反映されない | Maven で JAR を作り直してから、バックエンドの Docker イメージを再ビルドする。再起動だけでは更新されない |
| 再起動しても初期データに戻らない | Keycloak は DB にある既存の Realm を優先し、起動時のインポートをスキップする。停止・再開ではデータは初期化されない |
